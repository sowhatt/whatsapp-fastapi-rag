2. CARTOGRAPHIE TECHNIQUE ET ISOLATION

Notation : -> clé étrangère réelle ; ~> référence logique sans FK.
Les PK sont id, sauf exceptions précisées. Le schéma historique exact d’une
copie réelle reste à inventorier ; la cartographie décrit les modèles courants.

merchants
  Racine tenant ; identité WhatsApp unique. Aucune identité exportée par l’audit.
shops -> merchants
  merchant_id obligatoire ; UNIQUE(merchant_id,code).
merchant_users -> merchants
user_shop_memberships -> merchant_users, shops
  UNIQUE(user_id,shop_id), rôle et activation ; autorisations établies par les
  dépendances PWA/RBAC. La cohérence utilisateur/boutique n’est pas une FK composée.

suppliers -> merchants, shops
  merchant_id et shop_id historiques nullables ; dette entière stockée dans debt.
  UNIQUE(merchant_id,shop_id,name) ; index partiel UNIQUE(merchant_id,name)
  WHERE shop_id IS NULL. Les noms ne constituent pas une identité interboutiques.
  Les NULL merchant_id conservent la sémantique PostgreSQL des unicités : ils
  exigent une revue préalable, pas une déduction automatique d’appartenance.

purchases -> merchants, suppliers
  Pas de shop_id direct. merchant_id/supplier_id nullables historiquement.
  total_amount, paid_amount, remaining_amount en entiers XOF ; original_amount,
  original_currency et exchange_rate documentent la devise source, sans modifier
  la devise comptable de total_amount. initial_paid_amount nullable est le
  snapshot initial, pas le payé courant. status, échéance et annulation conservés.
purchase_items -> purchases, products
  Quantité, coût, montant, payé et restant par ligne ; pas de merchant_id/shop_id.
supplier_payments -> merchants, purchases, suppliers
  purchase_id obligatoire, supplier_id nullable pour les achats cash anonymes.
  amount et paid_at ; les versements initiaux sont déjà des SupplierPayment.
supplier_payment_allocations -> supplier_payments, purchase_items
  Ventilation du paiement ; aucune FK ne garantit que les deux parents portent
  le même purchase_id. L’audit contrôle parenté, positivité et sommes par paiement
  ET par ligne. Il n’y a pas de registre distinct des soldes d’ouverture.

shop_operations -> merchants, shops, merchant_users
  UNIQUE(entity_type,entity_id) ; entity_id ~> achat, vente, dépense, etc.
  Pour un achat, c’est la preuve de boutique. Son absence ne signifie pas
  « boutique principale ». La référence polymorphe n’a pas de FK vers l’entité.
products -> merchants, categories
  Catalogue partagé entre boutiques du même commerce ; ancien stock global.
shop_inventories -> merchants, shops, products
  UNIQUE(shop_id,product_id) ; stock courant et initial_stock nullable.
  Le stock d’une boutique ne se déduit pas de products.stock.
stock_movements -> merchants, products
  reference_type/reference_id ~> purchase ou sale ; pas de shop_id direct.
  Boutique retrouvée via ShopOperation de l’entité ; mouvement sans provenance,
  tenant divergent ou type non résolu signalé, jamais attribué par défaut.
transaction_events -> merchants
  Journal logique entity_type/entity_id, sans FK polymorphe ; source de preuve
  complémentaire à consulter lors d’une revue autorisée, pas crédit d’ouverture.

sales -> merchants, customers ; sale_items -> sales, products
sale_photo_imports -> merchants, shops, sales
  UNIQUE(merchant_id,shop_id,source_sha256,row_number), payload_hash,
  stock_applied. Un import papier historique ne décrémente pas nécessairement
  le stock courant ; ne jamais rejouer ses mouvements pour « réparer » un solde.
sale_photo_drafts -> merchants, shops, merchant_users
  PK UUID texte ; CHECK confirmation totalement absente ou totalement complète
  (confirmed_at, confirmation_hash, response, audit) ; portée boutique/session.
purchasing_receipts -> merchants, shops, merchant_users
  PK(merchant_id,key) ; kind, payload_hash et réponse durable. La même clé doit
  conserver contenu, boutique et type. Reçus à préserver lors de toute restauration.

Isolation effective :
- app/db/tenant.py ajoute le filtre merchant_id aux SELECT ORM des modèles
  enregistrés lorsque le contexte existe. Il ne sécurise pas le SQL brut, ni
  une session sans tenant, ni le bypass explicite ; les lignes/allocations sont
  protégées via leurs parents et les services, pas par un filtre tenant direct.
- purchasing_integrity_service filtre les fournisseurs par merchant/shop,
  et les achats via ShopOperation merchant/shop. Les fournisseurs NULL shop sont
  exclus du parcours PWA. Les routes vérifient permissions et boutique active.
- Le verrou commerçant sérialise achat/règlement ; ordre commun commerçant,
  achat/fournisseur, produits, inventaires. READ COMMITTED imposé aux écritures.
  Reçus, dette, stock, allocations et événements sont dans la même transaction.
- Les FK sont simples ; aucune RLS ni FK composée d’appartenance n’est démontrée
  par les modèles/migrations. Le rapport JSON indique relrowsecurity effectif.
  Les tests montrent qu’un SQL privilégié peut créer une parenté inter-tenant
  malgré les FK. Le diagnostic la signale, les API refusent les accès hors scope.
  On ne peut donc pas certifier une isolation absolue des données historiques
  inconnues : nettoyage revu et contrôle des privilèges SQL restent obligatoires.
- Les CHECK financiers sont principalement applicatifs : total/payé/restant,
  allocations et statut doivent être audités même si les FK sont valides.

4. RÈGLES DE RÉCONCILIATION FINANCIÈRE

Pour chaque achat non annulé, en XOF entiers :
  T = total_amount ; P = somme des supplier_payments.amount liés à cet achat.
  I = initial_paid_amount si attesté, sinon NULL.
  Paiements ultérieurs U = P - I si I connu, sinon NULL.
  Total réglé = P (NE PAS calculer I + P, qui compterait deux fois l’initial).
  Reste dû calculé R = T - P ; ne pas plafonner à zéro un montant incohérent.
  Crédit initial de l’achat C = T - I si I connu, sinon NULL.
  Écart fournisseur = suppliers.debt - somme des R des achats actifs.

Contrôles indépendants : payé stocké = P ; restant stocké = R ; T = payé + reste ;
sommes de lignes = en-tête ; somme d’allocations = paiement ; allocations de
chaque ligne = payé de la ligne ; quantité x coût = montant de ligne ; montants
non négatifs, paiement positif daté, versement initial entre zéro et min(T,P).
Un statut inconnu, trop-payé ou allocation au mauvais achat produit une anomalie.

Les achats annulés n’alimentent ni achat actif ni dette courante. Leurs paiements
restent exposés séparément dans cancelled_payments : aucune annulation n’invente
un remboursement. total_settled du regroupement porte sur les achats actifs ;
le décaissement toutes opérations = total_settled + cancelled_payments.

Les sommes sont groupées par fournisseur/boutique prouvée, pas par nom.
Le groupe shop_id=NULL et attribution=QUARANTINED conserve les opérations dont
le scope achat/fournisseur/paiement est incohérent. evidence_shop_id montre la
preuve de l’opération sans la transformer en attribution valide.
Les autres anomalies détaillées restent bloquantes même si un scope est connu.

suppliers.debt est GLOBAL au fournisseur. S’il est partagé entre boutiques,
aucune dette historique n’est recopiée ou répartie sur les groupes :
historical_debt et debt_difference par boutique sont NULL. Le total historique
et son écart restent visibles une seule fois au niveau fournisseur, avec
raw_calculated_due et attribution_valid. Ne pas sommer les écarts NULL comme zéro.
Un fournisseur sans shop mais avec une unique preuve concordante peut présenter
un rapprochement provisoire par boutique ; candidate_shop_id n’est qu’une
proposition pour revue, jamais une instruction d’écriture.

Cohorte mixte : un seul I inconnu rend initial_paid_amount, subsequent_payments
et initial_credit agrégés NULL. known_initial_paid / known_initial_credit
conservent les sous-totaux attestés ; unknown_initial_count mesure l’incomplétude.
La date du premier paiement ne sert jamais de preuve du versement initial.

Distinction essentielle : crédit initial d’un achat != solde d’ouverture du
compte fournisseur. Aucun registre d’ouverture probant n’existe dans ce schéma.
opening_balance=NULL, opening_balance_status=UNKNOWN_NO_LEDGER, même si l’écart
est nul. Un écart de 750 sans achat n’est pas automatiquement un crédit de 750.
Il faut une pièce, une période d’ouverture et une validation métier explicites.

5. CLASSIFICATION DES ANOMALIES ET CORRECTIONS PROPOSÉES

Catégories cumulables : un fournisseur peut être sans boutique, sans achat et
avoir un solde incohérent. Une seule priorité masquerait des problèmes distincts.

1) UNAMBIGUOUSLY_ATTACHED : propriétaire valide, boutique explicite cohérente
   avec les opérations. Ce statut d’appartenance n’efface pas une dette erronée.
2) WITHOUT_SHOP : shop_id NULL ; BLOCKER. Proposition manuelle seulement avec
   preuve unique et concordante. Aucune sélection de la première boutique.
3) MULTIPLE_SHOPS : plusieurs boutiques d’achat ; BLOCKER. Préparer une scission
   approuvée, avec correspondance ancien/nouveaux IDs, achats ET paiements, sans
   dupliquer la dette ni fusionner sur un nom.
4) AMBIGUOUS : propriétaire invalide, scope absent/contradictoire, référence de
   paiement contradictoire, ou fournisseur non rattaché sans preuve ; BLOCKER.
   Obtenir les pièces et maintenir le blocage. candidate_shop_id reste NULL.
5) NO_PURCHASE : aucun achat, y compris annulé ; REVIEW. Vérifier fournisseur
   dormant, périmètre d’historique et dette d’ouverture ; ne pas supprimer.
6) BALANCE_MISMATCH : écart dette, payé ou restant ; BLOCKER. Rapprocher pièces,
   règlements, annulations et ouverture. Correction monétaire séparée et validée.

Chaque finding comporte reference (table:id ou clé technique), category,
severity, merchant_id si disponible, correction proposée. Les autres catégories
couvrent scopes achats/paiements/produits/stocks/imports, ShopOperation orpheline,
allocations, statut, montants et date. Le champ correction ne déclenche rien.

Exemples synthétiques validés :
- Achat 5 000, initial 1 000, ultérieur 1 000 : réglé 2 000, crédit initial 4 000,
  dû 3 000, dette 3 000, écart zéro ; aucun double compte du paiement initial.
- Même historique migré sans snapshot : initial/ultérieur/crédit initial inconnus,
  réglé 2 000 et dû 3 000 restent calculables.
- Dette augmentée de 123 : BALANCE_MISMATCH, écart +123, aucune correction.
- Fournisseur partagé, deux achats de 5 000 et initial 1 000 chacun : dû 4 000
  dans chaque boutique, dette globale 8 000 ; dette par boutique laissée NULL.
- Sans achat, dette 750 : NO_PURCHASE + BALANCE_MISMATCH, ouverture inconnue.
- Achat annulé : dette zéro, paiement historique 2 000 conservé séparément.

10. RISQUES RÉSIDUELS ET CHECKLIST MÉTIER

Risques bloquants avant GO staging définitif :
- Aucun échantillon historique représentatif autorisé rapproché ; fournisseurs
  partagés, absence de preuves, dette d’ouverture et erreurs de scope inconnus.
- Appartenance fondée sur contrôles applicatifs, pas RLS/FK composées ; revue des
  accès SQL/legacy et des sessions privilégiées indispensable.
- Effets de bootstrap legacy sur NULL tenants/coûts/numéros : audit avant startup.
- Pas de test de volumétrie/verrous en charge, de backup représentatif, de rôles
  réels, de PITR ni de RPO/RTO ; lecture d’audit globale en mémoire à dimensionner.
- Stock initial inconnu, ajustements hors opérations et journal incomplet ne
  permettent pas de promettre une reconstruction intégrale du stock historique.
  Le diagnostic contrôle les appartenances, pas un inventaire physique certifié.
- Les sources papier, auteurs, sessions, justificatifs et écritures d’ouverture
  ne sont pas validés par des sommes correctes. Un JSON sans anomalie ne suffit pas.
